# Feature Acceptance

## 核心原则

**验收项必须从需求派生，不能从实现派生。**

从实现派生 → 实现漏了的功能验收也漏、覆盖的是"代码有哪些分支"而不是"需求要求什么"、验收者被实现逻辑锚定。所以完整档要先**立锚**、再由**实现者之外的人**生成验收矩阵。

两条轨道，责任人不同：

| | 谁做 | 内容 |
|---|---|---|
| **自动验收** | Agent 全权 | L1 单测 / L2 集成 / L3 接口 / L4 端到端 / L5 铺垫（走查截图）——**跑完给结论** |
| **人工验收 L5** | 用户 | **只放需要业务判断的**：这是不是你要的东西、流程顺不顺、交互能不能接受 |

把"对比 spec 字段""核对表结构""确认测试有没有过""用 Swagger 试试"列进人工清单 = 分类错误。

**验收不是一次性动作。** 一个需求的验收周期内——中途的补充验证、修复后复验、被质疑后重新举证——**每一轮都按本 skill 走**，不要只在首次调用那一轮遵守。后续轮次里最容易松掉的正是隔离和证据纪律。

## 分档

**轻量档**——改动**不新增对外契约**，且**不触及任何一项「行为维度」**（定义见下方「覆盖率」）：

- 文案 / 样式 / 单点 bug 修复
- **不生成矩阵、不留档**，但两件事仍要做：
  1. 验证**原始问题已修复**（复现路径 + 结果）
  2. 若改动触及任一「行为维度」，**补一条该维度的反例**（写在回复里即可，不落矩阵）
- 产出：自动验收结论 + **明确写"无人工验收项"**（有 1–2 条业务判断项也可以）

**完整档**——命中任意一条：

- 新功能 / 新接口 / 新页面
- 涉及**钱、额度、权限、数据语义、不可逆操作**
- 跨端流程（前端 + 后端 + 定时任务）
- 多阶段交付（每个阶段都可走完整档）
- **部署 / 迁移顺序约束**（如 migration 必须先于代码）
- **改既有默认行为或展示 / 计算口径**（默认排序、默认筛选、统计口径）——措辞润色不算，口径变了才算
- 用户明确说"验收这个"

**「核心链路」指**：鉴权 / 配额 / 计费扣费 / 钱包余额 / 预算额度 / 数据写入与迁移 / 交付物下发；项目规则或 `CLAUDE.md` 标为"核心模块"的一律算。

**校准案例**（判不准时对照）：

| 改动 | 档 |
|---|---|
| 改一句错误提示文案 / 调列表间距 | 轻量（措辞与样式，行为口径不变） |
| 修一个偶发空指针 | 轻量（但要验原路径不再崩） |
| 给已有接口加一个可选字段 | **完整**（新增对外契约） |
| 改默认排序规则 / 改统计口径 | **完整**（改既有默认行为或口径） |
| 换 ORM / 加索引 / 改表结构 | **完整**（触及写入路径与顺序约束） |

> 拿不准就往**完整档**取。但也别无差别走完整档——流程重到没人愿意用，agent 就会开始形式化执行，比没有流程更糟。

## 完整档五步

### ① 立锚 —— **主 agent 自己做**

收集全部需求源，**必须发生在生成矩阵之前**：

| 源 | 典型位置 | 派生的验收项 |
|---|---|---|
| 需求文档 | `docs/specs/*` | 数据语义、状态机、计费规则、权限 |
| **设计稿 / 原型** | `docs/design/**`、HTML demo | 布局、视图切换、交互行为、空/加载/失败态、文案 |
| **用户决策** | 会话里拍板的规则 | **主 agent 有责任把它转写成文字**（写进 spec / 设计稿 / 决策记录）——不转写就会丢，验收者无从得知 |
| 项目规则 | `.claude/rules/*`、`CLAUDE.md` | 「用户标识必须渲染为可读名称」这类本身就是验收项 |
| 外部契约 | 上下游 API / 字段约定 | 兼容性、字段语义、错误码 |
| **持久化链路** | 前端 payload → IDL/proto 消息 → handler 赋值 → store 的 `InsertFields()` / `UpdateSQL` 列清单 → 表结构 | **字段是否真的能落库**：逐字段列一张「字段 × 各写入路径」对照表，**缺格即 finding**——比行为测试更早、更便宜地抓到静默丢字段 |
| 部署约束 | 迁移文件、ConfigMap、构建参数 | 顺序、构建时注入 vs 运行时配置 |

**只对需求文档做覆盖检查必然漏 UI**——UI/交互的验收项往往在 spec 里根本不存在。

**源之间冲突时不要自行裁决。** 矩阵里把冲突行标 `⚠️ 冲突`，写明两个源各说了什么，**升级给用户定**。常见冲突：spec 说必填 vs 设计稿画可选；项目规则说越权应拒绝 vs 某条决策说该场景放行；需求变更后旧 spec 与新决策不一致。

### ② 生成验收矩阵 —— **调用独立验收 agent（第一次）**

见 `references/verifier-subagent.md` 的 **Prompt A**。这次调用**只生成矩阵并停下**，不执行任何测试。

必须包含：

- 每行带锚点原话，**每个源分别做双向覆盖检查**（源→矩阵、矩阵→源）
- **锚点缺口检查**：源清单里是否缺了某一类？没有设计稿却有 UI 需求？一条决策记录都没有？→ 列为「锚点缺口」
- 冲突行标 `⚠️ 冲突`，不要自行裁一个
- 矩阵模板与边界维度清单见 `references/acceptance-matrix.md`

### ③ 重点提案 → 用户确认

把矩阵压成 3–5 行给用户，**确认后再开跑**：

```
【验收重点提案】<需求 / 阶段>
核心路径（高覆盖，含边界）：1. …  2. …
抽样：3. …
本次不验（out of scope）：…        ← 必须写，防止"以为验过"
锚点缺口 / 待裁决冲突：…           ← 没有就写"无"
→ 确认 / 调整？
```

**这道门不可省。** 不确认就执行，等于把"重点错了要返工"的风险全留给用户。

### ④ 执行 —— **调用同一个验收 agent（第二次）**

见 `references/verifier-subagent.md` 的 **Prompt B**。按**已确认的矩阵**执行 L1–L4 + L5 铺垫。

- 工作量超出单次调用预算时，**按层或按功能区块拆多次调用**（见 `references/verifier-subagent.md`「拆分退路」）
- **L5 铺垫**：用 `$browser-session-stability` 把主流程走一遍、逐步截图，产出带图的操作脚本给用户——用户只做判断，不做探索
- **无前端交互时（纯后端 / CLI / 定时任务）跳过走查**，并写明跳过原因，不要默默不做
- **进不去登录态 / 驱动不了浏览器时**：按项目约定取登录态——**通常是直接向用户要 token 或已登录会话，不要自己搭登录流程**。拿不到就标 ⚠️ 未验证 + 阻塞原因，并把它作为**一个明确的决策**交给用户（你来点 / 留到下轮 / 换个环境），**不要说"你要是顺手点一下"**
- **报阻塞前先实测根因**。没验证过的规律（"重启后端就掉登录态"）不许写进结论——编出来的因果会盖住真正的原因，还会让用户替你查

### ⑤ 报告 + 留档

见 `references/report.md`。默认 Markdown 矩阵；有 UI 截图 / 多轮失败对比 / 需要用户逐条勾选时，额外生成本地自包含 HTML。

**不做机器校验**：没有 receipt、没有 digest、没有 CI gate。就是一份人看的留档。

## 覆盖率

**「行为维度」共五项**（分档与执行都以这为准；reference 里为便于单独阅读会重复列出，口径以此为准）：

> 权限 / 金额额度 / 状态转换 / 幂等并发 / 非法输入

**反面用例按「行为维度」计，不按矩阵行、不按功能模块。** 命中哪个维度，就为该维度出一条"应该被拒绝"的用例。

只验正例是覆盖率的假象。矩阵行数多 ≠ 覆盖率高——30 行正例不如 20 行正例 + 5 个维度的反例。

**完整档必查维度**（细则与全部变体见 `references/acceptance-matrix.md`）：

时间 · 状态机 · 权限 · 金额额度 · 并发 · 幂等 · **写入路径** · 空满 · 异常路径 · 数据一致性 · 回归 · 顺序约束

## 写-读往返：凡「能填 / 能改 / 可见」的需求句，都要译成往返断言

需求里出现「某处能填 / 能改 / 可配置 / 可见」时，**验收项必须是「填 → 保存 → 重新读取」的往返**，而不是「控件 / 字段存在」。

| ❌ 只验到这一层 | ✅ 必须到这一层 |
|---|---|
| 表单里有「所属互斥组」下拉 | 选了互斥组保存 → **重新读取该商品**，互斥组还在、且就是它 |
| 配置页有 `app_id` 输入框 | 改了 `app_id` 保存 → 再读仍是新值 |
| 详情页显示了某字段 | 该字段的**每一条**写入路径都能改到它 |

**为什么单列一节**：静默丢字段在行为上**完全不可见**——不报错、返回成功、页面也正常，只有"重新读一遍"才发现。黑盒走查天然测不到，所以必须由矩阵显式要求。

**按「字段 × 写入路径」扫类，不做个案复核**：同一字段在不同写路径上是分开实现的（新建 / 列表编辑 / 专用保存页 / 导入各一段代码），一个字段在某条路径丢过，**同类字段在其他路径大概率也在丢**。

> **2026-09-29 实测两连**：① `app_id` 在「控制台保存」路径丢过（已修）→ 我让验收者复核的只是**那一条路径**，于是同类问题在「新建商品」路径活了下来（`mutex_group_key` 静默落 NULL → 组级持有上限整段失效）；② 它最终是**代码审查**抓到的，不在验收里——因为没有任何一条断言要求"读回来"。
>
> 教训：**把历史缺陷告知验收者时，必须同时要求它扫同类**（同字段的其他路径、同路径的其他字段）。只点名一条路径 = 替它把检查范围钉死在那一条上。

**最便宜的做法是列一张对照表**（不必写代码）：字段 × 各写入路径，逐格填"能否落库"；格子里写不出"能"的就是 finding。它比跑任何行为测试都早、都便宜。

## 独立验收者怎么落地

用**当前环境提供的子代理机制**起一个新上下文做验收。各 CLI 的原语叫什么名字是它们自己的事，这里不做适配表——**原则只有一条**：

> **支持就自己调用；确实不支持，再把情况和风险抛给用户定。**

**「支持不支持」必须先查，不能自陈。** 动手前**枚举当前可用的工具 / 命令**，找一遍有没有能开**新上下文**的原语（不论它叫什么名字）。只有确认列表里确实没有，才算"不支持"。**跳过查找、直接宣布"不支持"不算合规。**

- **"支不支持"是技术事实 → 你自己查证**，这不该甩给用户（它属于「跑个命令就能确定」那一类）
- **"不支持时怎么办"**（降级交付 / 改人工验 / 本轮放弃）**→ 这才是要用户拍板的**

不要因为"没有现成机制"就顺手在主上下文里自己验完——那是静默降级。

**硬指标**：执行验收的那个上下文里，**没有实现过程的痕迹**。

**自我检查**：动手前确认三件事——① 我真的起了**新的上下文**，不是在自己脑子里过一遍、也不是"我换位思考一下"？② 喂给它的东西里没有实现 diff、改动文件清单、实现者的解释？③ 它用的是新上下文，不是复用主会话？

**没隔离就申报**：若最终是在未隔离状态下得出的结论，**在结论里显式写"本轮验收未隔离，退化为自我复核"，并说明卡在哪一步**。

**这句申报是红旗，不是模板。** 如果它开始频繁出现，说明选用的环境或流程有问题——**停下来跟用户确认，而不是习惯它**。

**静默降级的验收比没有验收更危险**——它带着"已验证"的标签。

喂给验收者的：需求源路径、已确认提案、环境信息（怎么起服务 / 怎么连库 / 数据在哪 / commit）、上一轮报告路径。
**不喂**：实现 diff、改动文件清单、实现者的设计说明与权衡解释、主 agent 对实现质量的判断。

允许与禁止的边界：**用实现来知道怎么测，用需求来决定对错。** 允许读实现代码定位接口/表名/错误码；**L4 / L5 层不看实现**，纯黑盒。

## 回传与隔离

验收 agent **只回传**：

1. **隔离方式**：实际用什么工具 / 命令起的新上下文；没做到就写"未隔离 + 卡在哪一步"
2. 矩阵状态表（**每行都带证据列，✅ 行也要**，可只写一行摘要）
3. 失败项：现象 + 期望 + **完整证据 + 复现命令**
4. 未验证 / 阻塞项及原因
5. 最不确定的 3 件事
6. 详细产物路径

第 1 项不是机器校验，只是**让你和我能把"隔离"这件事从自称变成写明**——一句话成本，但它是唯一能事后复核隔离真的发生了的东西。

**判定只由验收者给。** 主 agent 不得自己对验收项打 ✅——哪怕证据就摆在眼前（比如用户发来的截图）。看到什么，转给验收者去验。

**用户给的截图 / 录屏 / "我点过没问题" 都不是验收证据**，只能当**线索**（提示你去看哪里）：你控制不了它的视角、确认不了它的时效（是不是改动前拍的）、也没法用它触发交互。截图里的对勾是**待验证项**，不是已通过项。

完整日志、截图、逐条原始输出**落盘**，只给路径。主 agent 拿到后只决定修复还是派单，**不要把验收过程灌回主上下文**。

要求验收 agent 额外回答「**我最不确定的 3 件事是什么**」——低成本拉高置信度的实用开关，比多说十句"已验证"有用。

## 失败回环

失败 → 修复 → **重跑「失败项 + 相关回归项」**：

- 不能只重跑失败项（修复会带回归）
- 也不能全量重跑（太贵）
- **修复者 ≠ 本轮验收者**，保持分离
- **修完要扫同类**：同一模式在别的字段 / 别的写入路径 / 别的模块是否也存在？（`app_id` 修完没扫类 → 同类在「新建商品」路径活了下来）。修一条、顺手扫它的类。

**修复方应当拿到**：矩阵全文 + 失败项完整证据 + 复现命令。隔离的目的是"不让实现影响验收"，**不是"不让修复者看到证据"**——看不到复现命令就没法修。

**复验由原验收者做**（它知道上次怎么失败的）：用当前环境能续接同一上下文的方式找回它；找回不了就**重新起一个，并把上一轮报告文件喂给它**——复验不依赖记忆，依赖落档。

## 报告与留档

**三态，不是两态**：✅ 通过 / ❌ 失败 / ⚠️ **未验证**（附原因）。未验证默认阻断交付，必须显式写出。

**必须声明覆盖边界**（对应代码审查侧的 `review_evidence` 要求）：报告里要有一段写清 **① 哪些源 / 契约面是被逐条执行验证的 ② 哪些只是机械核验**（如 DDL 规则、审计调用点、算价入口是否唯一）**③ 哪些完全没覆盖**。不写这段，报告会被读成"全都验过了"——2026-09-29 就是事后才补上"新建路径没被覆盖"这句，而那条路径正是漏掉缺陷的地方。

**每条"通过"必须带证据**（命令 + 输出摘要）。只报"跑过了"= 不算证据，置信度为零。

抬头几行元信息，能回溯即可：**commit + 环境 + 数据规模**。不要做成校验机制。

**留档**：放项目已有的验收目录，命名 `<需求名>-<范围或阶段>-<YYYYMMDD>.md`。需求名做前缀即可按需求聚合，**不要再套一层子目录**。历史报告**保留不覆盖**。

**这份报告是下次同类验收的回归基线**：

- 改相邻功能时**继承上次矩阵增量修改**，不重写
- 上次 **❌ 失败过的项标为高危区**，这次重点验
- 上次 **⚠️ 未验证项**条件具备时补上；上次 out of scope 若进范围必须新增验收项
- **失效判据**：需求变更 / 大重构 / 环境更换 / 中间有他人改动 → 旧锚点作废，重新立锚

选哪一份作基线、以及目录发现手段，见 `references/report.md`。

## L5 人工验收

- **少而准，≤5 条**，并给出预计耗时
- 每条写清：**确切入口 → 操作 → 看到什么算通过**
- **前置就绪**：附确切数据位置 / URL / 账号，别让用户自己找
- 只覆盖：业务判断、UI/交互体验、真实数据观感
- **不需要业务判断就直说"无人工验收项"**，不要硬凑

## 交接纪律（写"你可以做的"之前先过一遍）

对**每一条**要交给用户的事问一次：

> 这条需要**业务判断**，还是**我跑个命令就能确定**？

后者自己做掉，给结论。

- **服务由 Agent 自己起 / 复用**。禁止写"你用 `make dev` 起后端"。项目已有 dev server 就复用；要重启就自己重启。
- **交接前确认跑着的是新代码**：查进程启动时间、健康检查、新路由是否生效。新写的路由返回 404，八成是**旧进程还在跑**——这是你该发现的，不是用户该踩的。
- **启动 / 验证命令必须核对过**（Makefile / package.json / 项目规则），不凭印象写。
- **接口层验证永不进人工清单。**
- 交付前先确认**自动验收已跑完**，而不是"写完了，你来试"。

## 反模式

- ❌ 验收项从 diff / 实现反推，而不是从需求源派生
- ❌ 只对 spec 做覆盖检查，漏掉设计稿、项目规则、口头决策里的可验收约束
- ❌ 矩阵生成后不等用户确认重点就开跑
- ❌ 锚点源互相冲突时自行选一个当准
- ❌ 在**同一上下文**里"假装自己是独立验收者"
- ❌ 没真正隔离却静默按"已验证"交付——必须写明"本轮验收未隔离，退化为自我复核"
- ❌ 把 schema/字段与 spec 的比对列成"请你确认"清单
- ❌ 人工验收清单里放"跑一下 build""确认测试通过""用 Swagger 试试"
- ❌ 「你用 `make dev` 起后端」——服务由你起 / 复用，且命令要核对过
- ❌ 服务**已经在跑**还让用户去起；跑的是旧进程（404）而没自己发现
- ❌ 交付纯后端阶段时硬塞"你可以试试"来填满人工验收段
- ❌ 「你要是有空，顺手点一下看看」——把**功能正确性**伪装成 L5。比"你用 Swagger 试试"更隐蔽，但一样是推给用户
- ❌ 拿用户的截图 / 录屏 / "我点过没问题" 当验收证据
- ❌ 主 agent 自己对着证据打 ✅，而不是转给验收者
- ❌ 报阻塞时给一个**没实测过**的根因（"重启后端就掉登录态"）
- ❌ 只验正例，没有命中行为维度的反面用例
- ❌ **状态机只验"非法转换被拒"，不验"合法流转能成功"**——前者抓不到"合法路径被守卫误拒"。2026-09-29 实测：一个守卫把「已售账号恢复服务」整条合法路径挡死，**两轮验收都没抓到**，因为代码里三条测试反把这个错误行为断言成了正确的（"代码错了、测试固化了错"）。判据补一条：**每条合法流转都要有一条正例**
- ❌ 「表单里有这个控件」就判 ✅（要验「填 → 保存 → **读回来**」）
- ❌ 把已知历史缺陷当**个案**复核，而不扫同类字段 / 同类写入路径
- ❌ 报告只列验了什么，不写**没验什么**（覆盖边界）
- ❌ 无证据的 ✅（没写怎么验的、没贴输出）
- ❌ 把失败 / 跳过项吞掉，只报通过的部分
- ❌ 用直接改 DB 的方式构造测试状态
- ❌ 没 restart 就测；测完给不出可复现命令
- ❌ 造数据脚本产出与用户手上要用的数据不是同一批
- ❌ 给这套流程加 receipt / digest / CI gate —— 留档是给人看的，不是给机器校验的
