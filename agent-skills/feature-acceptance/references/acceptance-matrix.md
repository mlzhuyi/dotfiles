# 验收矩阵

矩阵是「需求源 → 验收项」的映射表。它存在的唯一理由是：**让验收项可追溯到需求，而不是可追溯到代码。**

**只有完整档生成矩阵。** 轻量档不生成、不留档（见 SKILL.md「分档」）。

## 模板

| ID | 验收项 | 锚点（源 · 位置 · 原话） | 层 | 方法 / 断言 | 边界变体 | 责任人 | 状态 | 证据 |
|---|---|---|---|---|---|---|---|---|
| A1 | CSV 导入：合法文件整批入库 | spec §4.2「首行是表头，结算日必填」 | L3 | `POST /import` → 查库计数 | 重复行 / BOM / 缺列 / 结算日 31 | Agent | ✅ | curl 输出 + SQL 计数 |
| A2 | 同商品内 identity 唯一 | spec §3.1 `uk_product_identity` | L2 | 集成测试插重复值 | 跨商品可重复 | Agent | ✅ | `go test -run TestX -v` |
| B1 | 账号管理页三视图切换 | 设计稿 `direction-approved.md`「[列表][日历][工作台]」 | L5 | 点三个 tab，筛选条件保持 | 无数据时的空态 | 用户 | ⚠️ | 截图见附件 |
| C1 | 越权改他人账号被拒 | 项目规则 + spec §5 权限 | L3 | 用非管理员 token 调 | 同租户 / 跨租户 | Agent | ❌ | 返回 200，应为 403 |
| C2 | 结算日语义（月末截断 vs 顺延） | spec §3.3「31 号」 **vs** 决策记录「自然月顺延」 | — | **待裁决** | — | 用户 | ⚠️ 冲突 | 两源说法不一，见下 |

**状态只有三态**：✅ 通过 / ❌ 失败 / ⚠️ 未验证（附原因）。**不存在"看起来没问题"。**

**证据列每行都要填**，✅ 行也不例外（一行摘要即可）。空证据列的 ✅ 视为无效。

## 锚点来源清单（逐个源做覆盖检查）

| 源 | 去哪找 | 能派生什么 |
|---|---|---|
| **需求文档** | `docs/specs/*` | 数据语义、状态机、计费、权限、生命周期 |
| **设计稿 / 原型** | `docs/design/**`、`design-demos/*.html`、方向确认记录 | 布局、视图切换、交互行为、空/加载/失败态、文案措辞、视觉 token |
| **用户决策** | 会话中拍板的规则 | 任何"就这样""按你说的"背后的约定——**由主 agent 在立锚阶段转写成文字**，不转写就会丢 |
| **项目规则** | `.claude/rules/*`、`CLAUDE.md` | 「用户标识必须渲染为可读名称」「金额输入框焦点全选」「未分组置顶」「从库不承载写路径」等可直接验收的约束 |
| **外部契约** | 上下游 API / 字段约定 / Swagger / IDL | 兼容性、字段语义、错误码、必填性 |
| **持久化链路** | 前端 payload → IDL/proto 消息 → handler 赋值 → store 的 `InsertFields()` / `UpdateSQL` 列清单 → `sql/schema` | **字段能否真的落库**：逐字段 × 各写入路径的对照，缺格即 finding。静默丢字段在行为上不可见（接口 200、页面显示"保存成功"、值是空的），必须靠这张表抓 |
| **部署约束** | 迁移文件、ConfigMap、构建参数 | 顺序（migration 先于代码）、构建时注入 vs 运行时配置 |

> **只对 spec 做覆盖检查必然漏 UI。** 本项目 stock-plan 就是例子：spec §3 只管数据模型，三视图切换、批量操作条、日历联动全在设计稿里，spec 里根本不存在。

## 双向覆盖检查（每个源分别做）

1. **源 → 矩阵**：该源里每一条可验收的陈述，是否都有归属行？没有 = **漏验收**，补上。
2. **矩阵 → 源**：每一行能否指回该源的原话？指不回 = **与原始内容无关的验收项**，删掉。

两个方向都要跑。只跑一个方向，要么漏、要么虚胖。

统计口径：**各源的条目数 vs 矩阵行数**，作为提案的覆盖证据交给用户。

## 锚点缺口检查

双向检查只能验证**已列出**的源。对"从没被告知的源"，它没有任何报错能力——这是一类**自身质量门抓不到的静默漏验收**。

所以生成矩阵时必须额外回答：**我拿到的源清单里是否缺了某一类？**

- 有 UI 需求，却没有设计稿 / 原型？
- 涉及权限，却没有权限规则来源？
- 是长期迭代的功能，却一条历史决策记录都没有？
- 改动触及写入，却没有部署 / 迁移约束来源？
- 新增或修改了**可写字段**，却没去看持久化链路（proto 消息 ↔ handler ↔ store 列清单）？

缺什么就报什么，列为「锚点缺口」交给主 agent 补。

## 源冲突：标注，不裁决

当两个源对同一行为给出矛盾说法，**不要选一个当准**，该行标 `⚠️ 冲突` 并写明：

```
C2 | 结算日语义 | spec §3.3「31 号」 vs 决策记录「自然月顺延」 | ⚠️ 冲突
   源 A 说：…（原话）
   源 B 说：…（原话）
   需要用户裁决后才能验收
```

常见冲突：spec 说必填 vs 设计稿画可选；项目规则说越权应拒绝 vs 某条决策说该场景故意放行；需求变更后旧 spec 与新决策不一致。

冲突项在用户裁决前**不进入执行**，也不许按任一源"先验着看"。

## 边界维度全部变体

对每个验收项，过一遍这些维度挑适用的：

| 维度 | 具体变体 |
|---|---|
| **时间** | 月末 31→30→31、跨月、跨年、闰年、时区（本项目 `Asia/Shanghai`）、夏令时无关性 |
| **状态机** | 每个状态的进入条件、离开条件、**非法转换被拒**、终态不可逆；**并且每条合法流转都要有一条正例**（断言它能成功）← 只验"非法被拒"验不出"合法被误拒" |
| **权限** | 越权、跨租户、角色边界、未登录、自己审批自己（若业务允许则**必须能通过**） |
| **金额 / 额度** | 0、负数、超限、并发扣减、精度与舍入、向上取整边界 |
| **并发** | 同一资源抢两次（恰好 1 个成功）、重复提交、幂等键、锁粒度 |
| **幂等** | 重复点击、重复导入、重试、刷新页面、脚本连跑两次 ← **真实 bug 最高发区** |
| **写入路径** | 每个可写字段 ×（新建 / 列表编辑 / 专用保存页 / 导入）是否都能落库；某条路径漏了解析、漏了 store 的列清单、漏了回传 ← **只在一条路径可写的字段 = 静默丢配置**（见下「字段 × 写入路径」） |
| **空 / 满** | 空列表、空字段、NULL vs 零值、批量上限、真实规模（不是 2 条样例） |
| **异常路径** | 下游失败、超时、部分成功、回滚完整性 |
| **数据一致性** | 跨表写入是否同事务、聚合表与明细是否对得上、schema 与 migration 是否同步 |
| **回归** | 改动触及的既有功能、共用函数的所有调用方 |
| **顺序约束** | 迁移先于代码、开关先于流量、灰度顺序、构建时注入的变量 ← **单列，错了上线即炸** |

## 「字段 × 写入路径」对照表（成本最低、恰好补上行为测试的盲区）

只要改动**新增/修改了可写字段**，就列一张这样的表，逐格填"能否落库"。**填不出"能"的格子 = 一条 finding。**

| 字段 | 新建 | 列表编辑 | 专用保存页（控制台 / 配置 Tab） | 导入 | 批量操作 |
|---|---|---|---|---|---|
| `mutex_group_key` | ❌ 曾丢（proto 无字段 + store 列清单缺） | ✅ | ✅ | — | — |
| `pricing_config` | ✅ | — | ✅ | — | — |

怎么判每一格（四道关，缺一格即丢）：

1. **前端 payload** 里带了这个字段吗？
2. **IDL/proto 消息**有这个字段吗？（proto 会**忽略未知 JSON 字段**——前端发了、消息没有 = 静默丢）
3. **handler** 解析并赋值进 model 了吗？
4. **store 的 `InsertFields()` / `UpdateSQL` 列清单**包含这一列吗？

> **为什么要单独列这张表**：这四道关里任何一道断了，表现都是"接口 200 + 页面显示保存成功 + 值没了"。黑盒走查、UI 截图、单测全绿都抓不到它——**只有"重新读一遍"或这张表能抓**。
>
> 真实教训（2026-09-29）：`app_id` 在专用保存页丢过 → 只修了那一条路径、只复验了那一条 → 同类问题在**新建**路径存活（第 1、2、4 道关全断）→ 组级持有上限整段失效。**修一条必须扫它的类。**

## 反面用例：按行为维度计

**颗粒度是「行为维度」，不是矩阵行、也不是功能模块。**

> 权限 / 金额额度 / 状态转换 / 幂等并发 / 非法输入
>
> （五项口径以 `SKILL.md`「覆盖率」为准）

- 按**矩阵行**计 → 30 行矩阵膨胀出 30 条反例，不可执行
- 按**功能模块**计 → 太粗，漏掉同一模块里的子场景
- 按**行为维度**计 → 一个改动命中几个维度，就出几条反例；没命中就不出

**轻量档同样适用**：改动触及上述任一维度时，仍要补一条该维度的反例（写在回复里即可，不必落矩阵）。

每类反例的具体形态：

- 越权操作被拒（同租户 / 跨租户 / 未登录）
- 超限被拒（额度 / 数量 / 频次）
- 并发抢同一资源只有 1 个成功
- 重复操作不产生副作用（幂等）
- 非法状态转换被拒
- 非法输入被拒（缺必填、格式错、超长、注入字符）

## UI / 交互验收项怎么派生

UI 项从**设计稿**派生，不是从代码。每类至少过一遍：

- **结构**：布局、视图切换、信息层级、导航层级是否过深
- **状态**：空态 / 加载态 / 失败态 / 禁用态 / 无权限态 ← 设计稿常只画正常态，**缺失的要补出来问**
- **交互**：批量操作浮现与消失、确认弹窗、撤销 / 重试、误操作恢复
- **文案**：措辞是否说清后果、错误提示是否**可行动**（告诉用户下一步做什么，而不是只报错）
- **可发现性**：入口用户能不能找到、需不需要额外解释
- **认知负荷**：完成一件事要几步、有没有"我该点哪"的困惑
- **数据真实感**：真实规模下的表现（100 条 vs 2 条）

这些项**用户能判断，但 agent 要先把路铺好**——所以 L5 铺垫要把主流程走一遍并截图（见 `report.md`）。
