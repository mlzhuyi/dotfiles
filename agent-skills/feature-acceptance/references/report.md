# 验收报告

## 不做机器校验

**没有 receipt、没有 digest、没有 CI gate、没有自动比对。** 这是一份给人看的留档，能回溯即可。

不要为了"证明验过"发明机制——那会把流程做重，然后没人愿意用。

## 报告形态：Markdown 为主，按需 HTML

**默认 Markdown**——轻、可 diff、能进仓库。

**升级为本地自包含 HTML** 的触发条件（满足任意一条）：

- 有 UI 截图要内嵌（L5 铺垫）
- 多轮失败 / 修复需要对比
- 需要用户**逐条勾选**验收
- 矩阵行数多到 Markdown 表扫不动（>40 行）

HTML 规范：

- **单文件自包含**，双击浏览器打开，无外部依赖、无 CDN
- 截图内嵌（base64 或同目录相对路径）
- 顶部汇总条：`✅ 42 / ❌ 3 / ⚠️ 2`
- 矩阵表可筛选（按层、按状态）
- 失败项默认展开，通过项折叠
- 提供勾选区让用户逐条确认——**用户只做判断，不做探索**
- 不用托管类产物工具，一律本地文件

## 目录发现（不要无脑新建）

放报告之前**先找项目已有的验收目录**：

```bash
ls docs/ 2>/dev/null | grep -iE 'accept|qa|verif|test|report'
find . -maxdepth 3 -type d \( -iname '*acceptance*' -o -iname '*qa-report*' -o -iname '*verification*' \) -not -path '*/node_modules/*'
```

- 命中已有目录 → **用它**，沿用它的命名习惯（即使它不叫 `acceptance`）
- 一个都没有 → 新建 `docs/acceptance/`（与需求目录平级）
- 项目有明确约定（`CLAUDE.md` / 贡献指南写了放哪）→ 以项目约定为准

命名：`<需求名>-<范围或阶段>-<YYYYMMDD>.md`

- **需求名做前缀**即可按需求聚合：`ls docs/acceptance | grep stock-plan` 就是该需求全部历史
- **不要再套一层按需求的子目录**——多一层目录反而分裂既有约定
- 历史报告**保留不覆盖**——回溯的价值就在于看到当时验过什么、当时怎么失败的

## 报告结构

```markdown
# <需求 / 阶段> 验收报告

- commit: <hash>      环境: <local / test / prod>
- 数据: <脚本 + 规模，如 seed_stock_plan.py，200 账号 / 55 订阅>
- 验收日期: <YYYY-MM-DD>
- 基线: <继承自哪一份报告，或"新建">
- 验收隔离: <用什么方式起的新上下文；若未隔离，写明卡在哪一步，并标注本报告结论需打折看>

## 结论
✅ N 通过 / ❌ M 失败 / ⚠️ K 未验证
**可交付**: 是 / 否（有 ❌ 或 ⚠️ 即否）

## 自动验收
| ID | 验收项 | 锚点 | 层 | 状态 | 证据 |
|---|---|---|---|---|---|
（证据列每行都要有，✅ 行写一行摘要）

## 失败项
### F1 <标题>
- 现象 / 期望 / 完整证据 / 复现命令

## 未验证项
- U1 <项> — <阻塞原因>

## 跳过的步骤
- <如"L5 铺垫：本阶段无前端交互，跳过走查"> — <原因>
- <如"L5 铺垫：进不去登录态，主流程未走查"> — <阻塞原因 + 已经试过什么>

## 本次不验（out of scope）
- <项> — <原因>

## 锚点缺口 / 待裁决冲突
- <缺哪类源 / 哪两源冲突，需要谁定>

## 人工验收（需要你，≤5 条）
1. <确切入口 URL / 路径> → <操作> → <看到什么算通过>
   （前置数据已就绪：<记录 ID / 账号 / 页面>）

## 最不确定的 3 件事
1. …
```

## 元信息只写这几行

**commit + 环境 + 数据规模**。够回溯就行，不要写成校验清单。

## 这份报告是下次同类验收的回归基线

改相邻功能 / 同需求下一个阶段时：

1. **继承上次矩阵增量修改**，不要每次从零重写
2. 上次 **❌ 失败过的项标为高危区**，这次重点验（历史失败处是回归高发区）
3. 上次 **⚠️ 未验证项**这次若条件具备，补上
4. 上次的 **out of scope** 这次如果进范围了，必须新增验收项

### 选哪一份作基线

同一需求名下会积累多份报告（历史保留不覆盖），按这个顺序选：

1. **范围 / 阶段匹配优先**：优先取 `<需求名>-<同一范围或阶段>-*.md` 里日期最新的一份——同阶段的上一轮才是真正的回归基线
2. **跨阶段继承**：没有同范围报告时，取该需求名下**日期最新**的一份，并在报告里写明"基线：继承自 X"，让用户知道回归面是从哪来的
3. **不要凭记忆选**：用 `ls docs/acceptance | grep <需求名>` 看实际有哪些，别猜文件名

### 失效判据

命中任意一条，旧锚点作废，重新立锚、重写矩阵：

- 需求变更（spec / 设计稿改了任意一条被引用过的内容）
- 代码大重构（模块边界、接口契约、表结构变了）
- 环境更换（本地 → test → prod，或基础设施变更）
- 时间跨度大到中间有他人改动（**用 commit 区间判断，不要凭感觉**）

## 交付时的呈现

报告写完后，**在回复里给用户的**只有：

- 三态计数一句话结论
- ❌ 失败项逐条（现象 + 期望）
- ⚠️ 未验证项及阻塞原因
- 锚点缺口 / 待裁决冲突
- L5 清单（带入口与前置数据位置）
- 报告文件路径

**不要把矩阵整表贴进对话**——那是落档的内容，用户需要时自己开文件。主上下文只留结论。
