# 独立验收 Agent

## 为什么要独立

同一个 agent 既写实现又做验收，会系统性偏移：

- 只验自己写过的分支 → 实现漏掉的功能，验收也漏
- 「我知道这里怎么运作」→ 跳过黑盒验证
- 按"我写的逻辑"判对错，而不是按需求判对错
- 主上下文塞满实现细节，验收时被这些细节锚定

## 怎么落地成真实的隔离（不要只在措辞上"独立"）

用**当前环境提供的子代理机制**起一个新上下文。各 CLI 的原语叫什么名字是它们自己的事，**不做适配表**——原则只有一条：

> **支持就自己调用；确实不支持，再把情况和风险抛给用户定。**

**「支持不支持」必须先查，不能自陈。** 动手前**枚举当前可用的工具 / 命令**，找一遍有没有能开**新上下文**的原语（不论它叫什么名字）。只有确认列表里确实没有，才算"不支持"。**跳过查找直接宣布"不支持"不算合规。**

- **"支不支持"是技术事实 → 你自己查证**，不该甩给用户
- **"不支持时怎么办"**（降级交付 / 改人工验 / 本轮放弃）**→ 这才是要用户拍板的**

不要因为"没有现成机制"就顺手在主上下文里自己验完。

**硬指标：执行验收的那个上下文里，没有实现过程的痕迹。**

### 自我检查（比机制本身更重要）

动手前过一遍，任一为否就不算隔离：

1. 我真的起了**新的上下文**吗？不是在自己脑子里过一遍、也不是"我换位思考一下"？
2. 喂给它的东西里**没有**实现 diff、改动文件清单、实现者的解释？
3. 它用的是新上下文，不是复用主会话？

### 做不到就申报

若最终是在未隔离状态下得出的结论（没起子代理、喂了实现细节、或确实没有可用原语），**在结论里显式写"本轮验收未隔离，退化为自我复核"，并说明卡在哪一步**。

**这句申报是红旗，不是模板。** 若它开始频繁出现，说明选用的环境或流程有问题——**停下来跟用户确认，而不是习惯它**。

**静默降级的验收比没有验收更危险**——它带着"已验证"的标签。

## 信息边界

**喂给验收者：**

- 需求源清单（spec / 设计稿 / 项目规则 / 外部契约的**路径**）
- 已确认的验收重点提案
- 环境信息：怎么起服务、怎么连库、数据在哪、commit
- 上一轮报告路径（增量 / 回归验收时）
- 明确要求：**贴实测输出，不要复述"已验证"**

**不喂：**

- 实现 diff、改动的文件清单
- 实现者的设计说明、权衡解释、"我这里是这么做的"
- 主 agent 对实现质量的判断

**允许与禁止的边界：**

> **用实现来知道怎么测，用需求来决定对错。**

- ✅ 允许读实现代码，用来定位接口路径、参数名、表名、错误码，构造测试
- ❌ 不允许因为"代码里就是这么写的"而判定该行为正确
- ❌ **L4 / L5 层不看实现**，纯黑盒，从用户视角出发

## 两次调用，不要合并

> **矩阵生成与执行必须分成两次调用。** 合并成一次，用户就没有机会在开跑前校准重点——这正是"重点错了要返工"的来源。

### Prompt A — 只生成矩阵，不执行

```text
你是独立验收者，与被验收的实现无关。本次任务【只生成验收矩阵，不执行任何测试】。

## 需求源（判定依据只认这些）
- <spec 路径>
- <设计稿 / 方向确认记录路径>
- <项目规则路径，如 .claude/rules/*>
- <外部契约路径>

## 任务
1. 生成验收矩阵（模板见 acceptance-matrix.md），每行必须带锚点原话。
2. 对**每个源分别**做双向覆盖检查：源→矩阵（有无陈述无归属）、矩阵→源（有无行指不回原话）。
3. **锚点缺口检查**：你拿到的源清单是否缺了某一类？——有 UI 需求却没有设计稿？一条决策记录都没有？
   缺什么就报什么，列为「锚点缺口」。
4. 源之间冲突**不要自行裁决**：该行标 ⚠️ 冲突，写明两个源各说了什么，留给用户定。
5. 标出你建议的「本次不验（out of scope）」范围。

## 环境（仅供理解范围，本次不执行）
- commit: <hash>   环境: <local / test / prod>   数据规模: <条数>

## 硬约束
- 不要执行测试，不要写代码，不要修改仓库。
- 判定依据只能是上方的需求源；可以读实现代码来理解接口与字段，但不能拿实现当对错标准。
- 不确定就说不确定。

## 回传格式
1. 矩阵全表（ID / 验收项 / 锚点 / 层 / 方法与断言 / 边界变体 / 责任人）
2. 锚点缺口
3. 待裁决冲突
4. 建议的 out of scope
5. 覆盖统计：各源条目数 → 矩阵行数
```

拿到回传后，**主 agent 压成 3–5 行重点提案给用户确认**，再进 Prompt B。

### Prompt B — 按已确认矩阵执行

```text
继续你的验收任务（你是同一个验收者）。以下是用户确认后的最终范围。

## 已确认的矩阵
<矩阵全文，含用户调整>

## 用户确认的调整
- 重点：…    抽样：…    不验：…

## 任务
1. 执行 L1–L4，逐项贴实测命令与输出摘要。
2. L5 铺垫：用浏览器把主流程走一遍、逐步截图，产出给用户的操作脚本。
   不判定"好不好用"，只把可观测事实（截图 / 文案 / 步数 / 空态）备齐。
   **若本功能无前端交互（纯后端 / CLI / 定时任务）→ 跳过并写明跳过原因。**
   **若进不去登录态 / 驱动不了浏览器 → 标 ⚠️ 未验证，写明阻塞原因和你试过什么，
   不要自行编造根因（"重启后端就掉登录态"这种没实测过的规律不许写）。**
   登录态按项目约定取（通常直接向用户要 token / 已登录会话），不要自己搭登录流程。
3. 对命中「权限 / 金额额度 / 状态转换 / 幂等并发 / 非法输入」任一维度的功能，
   补一条"应该被拒绝"的反面用例。

## 硬约束
- 每条结论必须带证据（命令 + 输出）。没有证据的写 ⚠️ 未验证，不许写 ✅。
- ✅ 行也必须填证据列（一行摘要即可），不许留空。
- 状态只有三态：✅ / ❌ / ⚠️（附原因）。
- 失败、跳过、阻塞项全部列出，不许吞掉。
- 允许读实现代码构造测试；判定对错只能依据需求源。
- 禁止修改仓库代码。发现代码 bug 只报告，不修。
- 不确定就说不确定，不要猜。

## 回传格式（只回这些，详细产物落盘）
1. 隔离方式：你实际是用什么工具 / 命令起的新上下文
2. 矩阵状态表（每行含证据列）
3. 失败项：现象 + 期望 + 完整证据 + 复现命令
4. 未验证 / 阻塞项：项 + 原因
5. 最不确定的 3 件事
6. 详细产物路径
```

> 「行为维度」五项的口径以 `SKILL.md`「覆盖率」为准。

## 拆分退路

单个 subagent 扛不动完整档时（源文件多、要读实现、要跑大量命令、要截图），**不要硬塞进一次调用**，按下面任一方式拆：

- **按层拆**：一个 agent 跑 L1–L2（纯逻辑 + 连库），另一个跑 L3–L4（接口 + 端到端），L5 铺垫单独一个
- **按功能区块拆**：把矩阵按功能切成几块，每块一个 agent，各自回传自己那块的状态表
- **矩阵生成与执行分开**（本来就要分开，见上）

拆分后由主 agent **合并状态表**再落档。每个子 agent 都适用同一套信息边界与回传纪律。

## 回传纪律

**回传 = 状态表 + 失败证据 + 阻塞 + 不确定项。** 完整日志、截图、逐条原始输出**落盘**，只给路径。

主 agent 拿到后只做一件事：决定修复还是派单。**不要把验收过程灌回主上下文。**

## 对抗姿态

明确要求验收 agent 额外回答：**「我最不确定的 3 件事是什么？」**

只会说"全部验证通过"的验收报告，置信度反而更低。同时要求它报告**它没能覆盖的部分**——诚实的负空间比虚假的满分有用。

## 失败回环

- 修复由**实现侧**做（原 agent 或新 subagent），**不要**让验收 agent 顺手改
- **修复方应当拿到**：矩阵全文 + 失败项完整证据 + 复现命令。隔离的目的是"不让实现影响验收"，**不是"不让修复者看到证据"**——看不到复现命令就没法修
- 修完**重跑「失败项 + 相关回归项」**：只重跑失败项会漏修复引入的回归；全量重跑太贵
- **复验由原验收者做**（它知道上次怎么失败的）：用当前环境能续接同一上下文的方式找回它；找回不了就重新起一个，**把上一轮报告文件喂给它**——复验不依赖记忆，依赖落档
